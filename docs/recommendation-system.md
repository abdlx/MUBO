# Mubo recommendation system

Mubo's scanner remains the catalog authority. The Next server sends public track metadata to a private FastAPI service when a recommendation surface is requested. PostgreSQL stores the catalog, append-only player events, recommendation impressions, and incremental taste projections. A worker processes events in sequence under a transactional advisory lock. A separate metadata analysis worker records rough genre-based mood/energy while audio embeddings are absent. Redis caches the metadata catalog briefly and catalog sync invalidates it; recommendation responses themselves are intentionally not cached because each request records a fresh impression.

Run with `docker compose -f docker-compose.yml -f docker-compose.local.yml up --build` after setting `MUSIC_PATH` in `.env` to an absolute host-accessible directory. Browse at `http://localhost:3000`. The base Compose file exposes port 3000 only inside the network for reverse proxy deployments. The first Home request syncs the music catalog. Services migrate on startup. Keep `POSTGRES_PASSWORD` and `RECOMMENDATION_API_KEY` private and change the local defaults before exposing this stack. Persistent volumes hold PostgreSQL and Redis data.

The player batches events to `/api/events`. Next replaces user IDs with `RECOMMENDATION_USER_ID`; this app currently has no accounts, so **all visitors share one taste profile**. Events have UUIDs for idempotence, session IDs rotated after thirty minutes of inactivity, source/surface, duration/ratio, impression IDs and model version. The service verifies that feedback's impression belongs to the same listener and track. Raw events are never overwritten. `track_affinity`, `artist_affinity`, and `album_affinity` update asynchronously from play, completion, skip, replay, save and like events. Older input receives an exponential 30-day half-life at projection time. Realtime invalidation and ongoing decay of already projected values are future work.

Candidate generation currently uses the scanned catalog and metadata similarity: artist, album and genre overlap. An inspectable heuristic combines track, artist and genre affinity, seed similarity, recency, skip counts and controlled exploration. A greedy sequence spaces artists and albums. Normal shuffle uses a seeded deterministic sequence, recent-play suppression and artist/album spacing. Smart Shuffle inserts a catalog recommendation every four to eight native items, adjusting that interval from attributed completions, likes and skips; additions are marked in the queue and carry impression IDs into feedback events. Autoplay requests a continuation on queue exhaustion. Track, artist, album and playlist radio controls, Quick Picks, taste profile and a diagnostics endpoint exist in the service API; Next proxies the public recommendation surfaces. A service outage returns 503 quickly, and player and Home keep their local library behavior.

Home obtains a structured module feed with Jump Back In, Quick Picks and Made For You when enough content exists. Module order depends on whether there is recent listening history. The existing library, album and artist sections remain discoverable and serve as the fallback when recommendations cannot load. Because this is a local library, recommendations cannot introduce music that isn't already scanned.

Run `PYTHONPATH=recommendation python -m unittest discover -s recommendation/tests -v` after installing `recommendation/requirements.txt` for ranking, shuffle and API contract checks. After the catalog has synced, run `docker compose exec recommendation-worker python scripts/seed.py` to create three synthetic taste profiles (`repeat-night`, `pop-morning`, `mixed-discovery`). To inspect rankings, send a service-key-authenticated POST to `/debug/track` with `{"user_id":"repeat-night","seed":"demo","limit":20}` from within the Compose network. Compare it with the other personas after the worker projects the new events. The service `/health` checks database connectivity.

Audio embeddings, decoded-signal analysis, collaboration, LightGBM, contextual module fatigue, personalized mixes and experimentation are not implemented. Adding real accounts and authorization is required before multi-user deployment. Dedicated PostgreSQL integration tests and a running Compose acceptance test remain necessary on a host with Docker.
